Skill（智能体技能）技术概念

一句话个人解释：Skill 是一份（或一套）写给 Agent 看的"作业指导书"：用一个带说明书的文件夹（核心是 SKILL.md），把某类任务的最佳做法、步骤和配套资源存下来，Agent 在遇到匹配任务时按需加载。它解决的问题是——Agent 很聪明但不了解你的流程，Skill 把"你试出来的正确做法"变成可复用的知识。

学习目标

  1. 能说出 SKILL.md 的基本结构（YAML 元数据 + 正文指令）及元数据的作用；
  2. 能解释"渐进式披露"：为什么 Skill 正文平时不占上下文、被用到才加载；
  3. 能区分 Skill 与 MCP、与工具（tool）的分工；
  4. 能动手写一个合格的项目级 Skill（本仓库的 concept-learning-kit 就是范例）。

核心问题

  • Q1：Agent 明明会写代码，为什么还需要 Skill？（→ §4）
  • Q2：Skill 是怎么被 Agent"发现并使用"的？（→ §5）
  • Q3：Skill 和 MCP、普通工具调用有什么区别？（→ §7）
  • Q4：什么样的知识适合沉淀成 Skill？（→ §7 使用边界）

概念定义与边界

是什么：Skill 是一种给 Agent 扩展能力的轻量机制：一个文件夹，里面有带 YAML 元数据（name、description）的 SKILL.md，可选再附脚本、模板等资源文件。Anthropic 的定义是：Skill 文件夹告知 Agent 如何完成某类任务——通常是流程知识而非纯代码能力。Agent 启动时只读取所有 Skill 的 name 和 description（很小）；当用户任务匹配某个 description 时，才加载该 Skill 的完整指令。这叫渐进式披露（progressive disclosure）。

不是什么：

  • 不是插件或程序——Skill 的主体是自然语言指令（可附脚本），它"教"Agent 做事，而不是替 Agent 做事；
  • 不是 API 连接器——给 Agent 接入外部系统的能力属于 MCP（见 §7）；
  • 不是一次性提示词——Skill 是可复用、可分享、面向一类任务的；只服务单一对话的一次性指令不需要写成 Skill。

核心机制或组成

📦 Skill 文件夹
SKILL.md + 可选资源 → 🔍 启动时只读元数据
name + description（很省上下文） → 🎯 任务匹配 description → 📖 加载完整指令进上下文

渐进式披露：平时几乎不占上下文，用到才加载——这是 Skill 与"巨型系统提示"的关键差异

  1. SKILL.md = 元数据 + 指令正文：YAML 头部的 name 与 description 是 Agent"发现"Skill 的唯一线索，description 必须写清"什么任务该用它"；正文是操作步骤、格式要求、注意事项；
  2. 可选的资源文件：脚本、模板、参考文档放在同一文件夹，正文里引用。脚本可以直接执行（确定性步骤交给代码），文档按需再读——避免一次性全塞进上下文；
  3. 存放位置决定作用域：放在 ~/.workbuddy/skills/（用户级，跨项目可用）或 项目/.workbuddy/skills/（项目级，随仓库分享给协作者）——本仓库的 .workbuddy/skills/concept-learning-kit/ 就是项目级；
  4. Skill 是写给人核查的：指令本质是"我们验证过的做法"，Agent 执行它，但人可以打开 SKILL.md 直接审阅、修改、版本管理。

应用案例：本仓库的 concept-learning-kit

场景：我每学一个新概念都要产出格式一致的学习资料（解释、机制、案例、辨析、自测、来源）。不写成 Skill 的话，每次都要在对话里重新描述一遍要求，容易遗漏、格式漂移。

走一遍流程：

  1. 我把要求写成 .workbuddy/skills/concept-learning-kit/SKILL.md：定义输入（概念名、深度）、九个固定章节、来源核查规则、自检清单；
  2. 在 WorkBuddy 里打开本仓库后，Agent 启动时读到该 Skill 的 description："接收任意新概念，生成结构化学习资料……"；
  3. 我对 Agent 说："用 concept-learning-kit 学习概念'检索增强生成（RAG）'"；
  4. Agent 加载完整 SKILL.md，按九章节模板生成 learning-materials/rag.html，并按自检清单逐项核对后才交付；
  5. 下次学任何新概念，同一套流程直接复用，产出风格一致。

概念如何发挥作用：我的"学习流程知识"从对话记录沉淀成了仓库里可版本管理的文件——这正是 Skill 的价值：把人验证过的做事方法交给 Agent 复现。本次作业的 agent.html、llm-context.html、skill.html 三份材料，就是按它生成的。

易混淆问题与使用边界

易混淆对区别标准
Skill vs. 提示词（prompt）提示词服务于当下对话；Skill 是持久的、面向一类任务的知识资产，可版本管理与分享。写进 Skill 的应是"以后还会这么做"的流程。
Skill vs. MCP（连接器）MCP 负责连接外部系统（给 Agent 新的"手脚"和数据源）；Skill 负责流程知识（教 Agent "怎么把事做好"）。二者常配合：Skill 指导调用哪些 MCP 工具。
Skill vs. 子 Agent / 工作流Skill 不改变 Agent 架构，只是注入指令；需要隔离上下文或并行分工时，用子 Agent 或固定工作流。

使用边界（我的判断标准）：

  • 适合沉淀：重复出现的多步流程、格式规范、易错点清单、领域约定；
  • 不适合沉淀：一次性的具体问题、含敏感信息（密钥/隐私）的内容——后者绝不能写进 SKILL.md 或随仓库提交；
  • description 写不好，Skill 等于不存在：Agent 靠它判断是否加载，要明确到"能判断当前任务是否匹配"；
  • 指令要可核查：Skill 里写"资料来源不得伪造"这类约束，比事后检查生成结果有效得多（本仓库 Skill 的"资料来源要求"一节就是为此设计的）。

自测题

1.（简答）为什么 Skill 启动时不加载全文、只读 name 和 description？这省了什么？ 要点提示：渐进式披露——上下文容量有限（见 llm-context.html），N 个 Skill 的全文常驻会挤占并稀释注意力。
2.（辨析）"让 Agent 能查数据库"该用 Skill 还是 MCP？"让 Agent 按我们团队的周报模板写周报"该用哪个？ 要点提示：能力接入用 MCP；流程/格式知识用 Skill。
3.（简答）一个 Skill "从不被触发"，最可能的原因是什么？怎么排查？ 要点提示：description 太含糊，Agent 无法把当前任务匹配上；排查法：对照任务描述重写 description。
4.（开放）为什么说 Skill 文件夹"适合放进 Git 仓库做版本管理"？放仓库里（项目级）和放用户目录（用户级）各适合什么场景？ 要点提示：SKILL.md 是纯文本、可 diff、可评审；项目级随仓库共享给团队，用户级服务个人跨项目习惯。
